## Direction

Prefer a provider's documented API or an authorized structured web endpoint over extracting data from rendered pages when the provider permits that exact use. Use page automation only when it is the approved, supported route or when no permitted structured interface exists. Keep each provider behind its own adapter and the current durable-worker contracts; do not build a generic endpoint scraper that guesses routes or replays arbitrary browser requests.

“Reverse endpoint” here means a structured HTTP/RPC request observed in a first-party web application, but not necessarily a public or stable API. Discovery in browser traffic does not establish authorization, entitlement, service-level guarantees, or permission for unattended polling. A source is enabled only after its endpoint, access method, request cadence, data use, and permitted account are confirmed. User-provided source permission does not justify defeating login, CAPTCHA, rate limits, bot checks, or other access controls.

The user has stated that they hold express written permission for the requested sources. The private grant is not stored in this repository. This inventory does not infer that each individual reverse RPC, account credential, quota, or unattended polling pattern is covered unless its scope is recorded; this is a documentation/access-scope gap, not a request to obtain permission again.

## Current implementation checkpoint — 2026-11-14

The ordinary flight flow now dispatches all-source adapters with bounded concurrency (default 2, hard maximum 4), publishes each normalized result to durable job progress, records the persistence timestamp, validates route-level partial previews before sending them, and renders previews before final completion. Per-provider HTTP latency is captured in bounded histograms with estimated p95 upper buckets; nested source metrics roll into enclosing flight/calendar operations and regional progress snapshots are immutable. Google Flights native RPC calls also expose a separate per-query fixed-bucket latency histogram. These do not provide cross-job p95; other browser/RPC paths remain outside timing telemetry. Booking.com Demand API shares the durable provider cooldown across jobs, honors Retry-After, does not automatically retry its POSTs, and rejects decoded JSON bodies above 2 MB. Ignav, Expedia partner, Skyscanner and Omkar JSON responses and Air Canada NDC XML are capped at 10 MB; Ignav airport metadata is capped at 1 MB. ITA Matrix API results are streamed under 5 MB and its API/browser parsers reject larger batches; browser body buffering remains a Playwright limitation. Matrix homepage key discovery is capped at 2 MB and its linked script at 5 MB. ACV currency-terms HTML is capped at 2 MB; the widget suggestions RPC now rejects declared or decoded responses above 1 MB before JSON parsing. Playwright may buffer that response before application inspection, and package listing pages do not yet have a uniform byte cap. Evidence and limits are recorded in [the progressive-results and transport implementation note](reverse-endpoint-progressive-results-2026-11-14.md) and [the ACV suggestion response bound note](acv-suggestion-response-bound-2026-11-14.md).

This does **not** mean every listed reverse endpoint is fully implemented, authorized, configured, or live-verified. It does not close source entitlement, RPC stability, per-source policy/pacing, end-to-end persistence-to-render p95, or live provider acceptance. The adapter inventory below continues to describe those gates.

## Current transport controls by adapter

These are code-level safeguards, not provider-published quotas or permission records. In production, `fetchSource` uses a durable shared per-provider minimum gap of 1,000 ms by default (`TRAVEL_SOURCE_GAP_MS` accepts 100–60,000 ms), honors `Retry-After`, applies at least 60 seconds of cooldown after HTTP 429, 300 seconds after 401/403, and 30 seconds after a final HTTP 5xx without a longer hint. Safe GET/HEAD requests may retry once after transient network/eligible server failures; the server-error cooldown starts after the retry fails. POST requests are not retried unless a source explicitly opts in. Local test fetchers can bypass the durable source policy. Regional calendars suppress a provider after an observed 5xx and continue healthy sources; query-local failures without an HTTP 5xx do not suppress other route pairs. Direct browser requests have their own pacing/deadlines and are excluded from the shared HTTP latency histogram.

## Adapter contract for every structured endpoint

Each source adapter must implement the following before it can contribute a user-facing price:

1. **Access record:** exact hostname/path/method, account or credential requirement, allowed purpose, rate/poll limits, and whether the endpoint is documented or a web-app RPC. Store no private captures, cookies, tokens, or full request headers in source control.
2. **Exact input:** preserve route, dates, trip type, actual traveler identities/ages or explicit counts, infant seating, cabin, currency, filters and room allocation where relevant. Reject unsupported query shapes before dispatch; never downgrade to a smaller or different party.
3. **Bounded transport:** source-specific timeout, request/response byte caps, abort/cancel propagation, concurrency limit, retry only when safe and allowed, `Retry-After` handling, and a shared per-source cooldown. No retry storm or poll loop.
4. **Strict response parser:** validate schema/version, query echo or equivalent request binding, currency, amounts, passenger/room scope, itinerary identifiers, route and chronology. Fail closed on incompatible or missing evidence; retain price-only observations separately from complete itineraries.
5. **Normalized evidence:** provider, endpoint/source label, exact query scope, source observation time, response time, source currency, all available tax/fee/baggage/fare details, segment-level timestamps and seller handoff. Do not infer CAD, taxes, ages, stops, duration, room equivalence, or seller availability.
6. **Coverage and errors:** distinguish no matching offer, unsupported request, unconfigured credentials, authorization failure, rate limit, upstream failure, timeout, parse drift, partial response and complete scan. Report searched and omitted routes/pages/polls and remaining budget.
7. **Regression and drift tests:** redacted response fixtures, parser tests for malformed/adversarial payloads, query-preservation tests, timeout/rate-limit tests, and an opt-in live check under an approved credential. A fixture proves parser behavior only, never live inventory.
8. **Safe handoff:** only create a link from the exact observed itinerary and provider-approved fields. Refresh the quote before calling it current. Never automate account creation, purchase, reservation, payment, CAPTCHA solving or access-control bypass.

## Fast search behavior

“Fast” means returning useful partial results early without weakening evidence or exceeding provider limits:

- Start independent, eligible provider requests concurrently, with a separate low concurrency ceiling and pacing policy per provider. One slow source must not hold completed sources behind an all-provider barrier.
- Persist each completed source result and publish it to the existing durable search job immediately. The UI should show the first validated offer as soon as its result reaches the job store; the calendar currently polls status about once per second, so the visible update should arrive on the next poll. Do not wait for final aggregation to render it.
- Reuse only an exact-query cached response inside that source's permitted freshness window. Cache keys must include route, exact dates/trip, full party/ages/seating, cabin, currency, filters and source version. Label cached observation time; never refresh its timestamp or present stale inventory as current.
- Keep hard request, result-page, byte and elapsed-time budgets. Stream provider status and progress separately from quote records; cancellation must stop in-flight requests and polls.
- Target low local overhead (under 250 ms p95 for validation, persistence and event publication after an upstream response) and a first-result UI update within one polling interval after persistence. These are engineering targets, not guarantees on provider response latency. Measure upstream latency separately by provider and query shape.
- Avoid sequential fan-out where policies permit concurrency. Do not parallelize requests when a provider requires serial polling, session affinity, or a single active browser lease.
