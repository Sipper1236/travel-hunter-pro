## Implemented

Normal multi-source flight searches now use a bounded two-adapter fan-out in `lib/providers.mjs`. Each source publishes its independently normalized result through the worker progress channel as soon as that adapter returns. A provider-specific unsupported party/input failure is retained as that source's status; selecting a source directly still fails closed. Provider fan-out concurrency is configurable only within a hard 1–4 limit, defaulting to two.

`lib/location-search.mjs` accumulates source results by exact airport pair. It builds a partial preview from fresh validated offers and price-only observations, preserves the submitted location labels and exact resolved airport routes, records source statuses and selected-pair coverage, and validates the preview with `flightWorkerResultError` before publishing. It reports per-provider sample/latest/max adapter elapsed times and elapsed time from the beginning of location resolution to the first source response. Timing is process-local, bounded to provider IDs, and is not a price freshness signal.

Shared HTTP calls now add a sanitized per-provider request-latency histogram to the source result: buckets are 0–100 ms, 100–250 ms, 250–500 ms, 500–1,000 ms, 1–2.5 s, 2.5–5 s, 5–10 s, 10–30 s, and over 30 s. `p95UpperBoundMs` is the upper edge of the bucket containing the 95th percentile; it is `null` if that observation lands in the open-ended final bucket or there were no requests. The summary stores provider labels, counts, HTTP status counts and latency aggregates only, not URLs, headers or payloads. Nested adapter metrics roll into enclosing flight/calendar operations while concurrent source contexts stay isolated. Regional progress retains immutable snapshots. This measures shared `fetchSource` traffic only; direct browser/RPC or SDK traffic may not be counted.

Google Flights native browser calls now expose a separate per-query `nativeRpcLatency` histogram in `nativeCoverage`. It uses the same fixed duration buckets and `p95UpperBoundMs` convention, records time from the call wrapper starting through accepted response capture (including failed or aborted calls), and contains aggregate counts only. It does not include browser startup, page navigation before the RPC wrapper, nor time spent parsing after capture. This source-specific measurement is not merged into shared HTTP metrics or a cross-job p95. The existing request ceiling remains 12 per query and captured RPC text remains capped at 8 MB; Playwright/browser buffering can precede the application cap. The Google native suite asserts three fixture RPC calls produce three latency samples and a consistent bucket total. Fixture timings establish instrumentation wiring only; they do not establish live latency or endpoint performance.

## Limits and next actions

- This implements faster dispatch and progressive rendering, not new provider endpoint access. Existing adapters retain their current credentials, entitlement, source policy, parser and rate limits. The code does not authorize new reverse endpoints or make private web RPCs stable/public APIs.
- Fan-out defaults to two across sources. Source-specific pacing, shared cooldowns, independent worker slots, and endpoint/account-specific scope records remain provider-specific work. The user has reported written permission for requested sources; exact Google/Matrix RPC and unattended-use/rate scope has not been recorded here. Expedia partner, Skyscanner, Air Canada NDC and Booking Demand credentials remain unconfigured where documented in the source inventory.
- Cache-hit progress reports cached provider statuses but has no adapter response latency. Cached observations retain their original freshness evidence.
- The current `firstResponseMs` includes location resolution and adapter wait; `providerLatencyMs` covers adapter duration. Request histograms are per query/job, not durable cross-job production aggregates. `persistedAt` is stamped when the job store accepts streaming progress, and the browser smoke test compares it to when the status region displays the result. The 387 ms controlled sample is not a p95 measurement and does not separate browser poll wait from receipt/render time. The 250 ms local-overhead target, end-to-end p95, direct browser/RPC latency and production-network latency are therefore **not verified**.
- The regional per-route planned count derives from the shared provider-ID list, preventing the source total from drifting when adapters are added.
- No live provider inventory was requested or used for this verification. No seller status, exhaustive coverage or booking completion is claimed.
