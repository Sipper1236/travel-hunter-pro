# Travel Hunter Pro

Local multi-source travel research prototype with a Next.js interface, provider adapters, and durable search workers. Full live-inventory, traveler-eligibility, seller-total, geographic-coverage, and deployment acceptance remains incomplete; see [`handoff.md`](handoff.md) for the detailed continuation guide, [`goal.md`](goal.md) for the active objective, and [`IMPLEMENTATION-STATUS.md`](IMPLEMENTATION-STATUS.md) / [`HANDOFF.md`](HANDOFF.md) for current status and dated evidence. Latest verification (2026-11-12): 539 tests pass, isolated production build passes, and dependency audit reports zero vulnerabilities. Requires Node 22.13 or later.

```sh
npm ci
npm run dev
```

In a second terminal in this project, start the travel search worker:

```sh
npm run worker
```

For one-command local development, use `npm run dev:stack`. It starts the loopback-only Next.js development server and durable search worker together, and stops both if either process exits or you press Ctrl+C. This is a local development convenience, not a production supervisor; production monitoring and worker recovery remain open. `npm run check:local-stack` verifies startup, healthy idle worker status, and coordinated shutdown on a temporary port and database without submitting a search.

Open http://localhost:3000. Both processes are needed for flight and vacation-package searches. `npm test` runs backend contract tests; `npm run build` checks the production build. Loopback Chromium UI smoke checks include `npm run check:accessible-controls`, `npm run check:responsive-ui`, and `npm run check:theme-contrast`; they intercept/block provider traffic and do not establish full WCAG or device conformance. `npm run check:calendar-ranges` is a controlled form check for the flexible calendar; it fixture-controls provider capability preflight and intercepts job creation, so it does not query a fare source.

## Current scope

Keep `.env.local` owner-only because it may hold partner credentials (`chmod 600 .env.local`). The local permission audit corrected its mode from `0644` to `0600` on 2026-11-14. This protects local access but does not encrypt credentials or complete the deployment secret-management gate.

The local `POST /api/search` API can query Google Flights, Ignav, Expedia Travel Redirect, Expedia via Omkar, Skyscanner, Air Canada NDC, and (when configured) an unofficial reverse-engineered ITA Matrix endpoint. Google's bundled api-anything `search` and `top` operations remain one adult, one-way, economy. A separate native Google Flights browser operation is enabled locally with `TRAVEL_GOOGLE_ROUND_TRIP=1` for bounded economy round-trip group searches without infants; it validates both directions and refreshes the original booking page without following seller continuations. Google calendar grids are enabled with `TRAVEL_GOOGLE_CALENDAR_RPC=1` for unfiltered one-adult economy round-trip date prices; these are price-only observations. One-way calendar searches use exact flight searches because the observed one-way grid operation is unsupported. The user states they hold written permission. Partner/API credentials stay server-side. Search displays CAD prices only, excluding other currencies without conversion; itinerary and handoff data are preserved where available. Quotes and links do not guarantee final seller availability. Air Canada also supports `OfferPrice` refresh. Nothing here creates a reservation or charges payment.

The Google Flights operation is unofficial and may drift or be blocked; use it only while written permission remains valid, never bypass challenges, and stop on blocks. Configure `IGNAV_API_KEY`, Omkar's `OMKAR_API_KEY`, Expedia Travel Redirect's partner-issued `EXPEDIA_TRAVEL_REDIRECT_KEY` and `EXPEDIA_TRAVEL_REDIRECT_AUTHORIZATION`, `SKYSCANNER_API_KEY`, and Air Canada's issued NDC credentials in `.env.local` to enable those sources. Expedia Travel Redirect now supports documented exact-date one-way and round-trip group listings with supplied child ages, validates linked legs and passenger fare-category counts, and refreshes by re-querying only the same flight identities. Flexible child calendars are excluded because the request does not include birth dates for age recalculation. Expedia credentials are absent in this environment, so its live results are unverified. Expedia via Omkar is one adult/one-way only; prices without explicit currency or exact one-traveler scope are not shown. Round trips through Omkar use an Expedia search link only; automated Selenium pricing is not enabled. ITA Matrix automatically discovers the public key used by its own web app; `ITA_MATRIX_API_KEY` is an optional server-side override, not a supported API credential. Matrix uses an unofficial endpoint for adult-count searches and its public browser form for economy family searches. Identified infant queries send lap/seat passenger-category counts derived from supplied DOBs and explicit seating after guardian/date-boundary checks; DOBs and traveler IDs stay local. Two live samples showed accepted category/group-total echoes, but they do not establish general carrier or fare eligibility. Family results require an echoed passenger-category count and the full CAD group total; up to three connecting or mixed-carrier results are expanded through Matrix itinerary details to validate segments, cabins and layovers. Matrix has no seller/booking confirmation and fails closed on unrecognized or incomplete itinerary data. Confirm permission and current access before using it. Skyscanner uses create/poll search and itinerary price refresh; Air Canada uses NDC `AirShopping` and `OfferPrice`. API Anything is a local runtime/catalog, not a hosted proxy; this app's Next.js routes form the local multi-source API. Paid-source routes are restricted to same-origin localhost requests. Fare calendars support exact-date pairs, return-date ranges and night ranges up to a 250 provider/date-search budget. Region lookup unions fresh OurAirports and Wikidata airport coverage and reports omissions; it does not claim exhaustive fare coverage. Flight + Hotel and Air Canada Vacations packages are separate durable search products, not automatically included as providers in the flight search results. Results do not prove market-wide coverage.

### Multi-source flight API

- The main form uses `POST /api/search/jobs` with `action: start | status | cancel | pause | resume | interact | remove`. Every request must include its UUID v4 `ownerToken`; start accepts it beside `input` and a unique `requestKey`, and status/control requests send it with the returned job `id`. The server stores only a SHA-256 digest and denies an ID without its owner capability. The tab keeps the token in `sessionStorage` to restore its job after reload. The durable queue allows up to five active jobs per owner and 20 across all owners. New job starts are limited to 10 per owner and 30 across the shared SQLite database per rolling minute; a limit response uses HTTP 429 and includes `Retry-After`. Idempotent retries do not consume start quota. These are local job controls, not user authentication or a distributed multi-instance quota; the service remains loopback-only.
- `POST /api/search` accepts `source: all | google | ignav | expedia | expedia-omkar | skyscanner | air-canada | ita-matrix`. Missing partner credentials are reported as `unconfigured`, not replaced with another source's price. Air Canada reports `unconfigured` until partner credentials are added.
- `POST /api/search/refresh` refreshes Skyscanner and Air Canada offers, re-queries the original Google booking page, re-queries Expedia listings while retaining only exact observed flights, or retrieves Ignav seller options. These are quote observations, not seller checkout confirmations.
- `POST /api/search/booking-links` performs an Ignav seller-link lookup. Expedia and Skyscanner handoff URLs are returned with their search offers.
- API Anything is used for Google Flights because that read operation is in the package's catalog. Expedia and Skyscanner's consumer pages returned DataDome/CAPTCHA challenge pages during API Anything capture, so the app uses their documented partner APIs instead and does not try to bypass those challenges. Air Canada uses the documented NDC 17.2 XML `AirShopping`/`OfferPrice` endpoints; partner access is required and the adapter is not live-verified here.

See `HANDOFF.md` for current setup and verification status; `work.md` retains the full product history and roadmap. The current Google source was live-probed on 2026-10-28 for YHZ→BCN, 2027-04-15; the returned CAD 673 itinerary was an observation only, not a seller-verified offer. An Ignav live YHZ–BCN search for 2027-04-15 returned 12 accepted CAD itineraries on 2026-10-29 UTC; seller availability remains unverified. Expedia, Skyscanner, and Air Canada NDC partner credentials are unset, so those live calls and refreshes are not verified in this environment.

CAD is requested from Google Flights using its currency and Canadian locale parameters; no conversion is calculated by this application. Region lookup uses the Wikidata entity and query services; matching and availability depend on those services.

### Ignav booking handoff and split-party comparison

Configure `IGNAV_API_KEY` in `.env.local` (copy `.env.example` first). The app never sends the key to the browser. “Check seller options” calls Ignav's booking-links endpoint for a specific fresh fare ID; returned HTTPS seller links and any reported link price are displayed. This is a handoff, not a reservation or guaranteed final reprice. Confirm all details with the seller.

“Compare split-party tickets” supports count-only adult groups of up to nine and identified parties when actual birth dates and guardian assignments are supplied. Every booking in a plan must preserve the exact marketed flights and UTC schedules in both directions. For count-only adult searches, the initial composition search cap is nine and the hard total is 30 including repeated lookups after interruption or stale-quote refresh; transport retries and seller-link lookups are additional. Requested flight filters apply to both directions and the CAD group budget applies to the combined total. Totals use integer cents, exclude expired quotes and disappear when the earliest quote expires. The result is bounded to queried party compositions and returned itineraries. Quotes may overlap inventory and do not prove all seats are available together. Each booking has its own Ignav ID and needs its own seller lookup. Count-based child/youth splits are disabled. Identified minors remain with their specified adult guardian, but carrier-specific fare eligibility and seller acceptance remain unverified. This comparison runs in the durable worker queue with progress, cancellation, pause/resume and reconnection after reload.

### Expedia and Skyscanner

Expedia uses the documented Flight Listings endpoint and requires partner onboarding credentials. Configure its issued key and full Authorization header value above. One offer must link both round-trip legs and include the complete CAD group total and passenger-category counts; the adapter rejects incomplete routes, mismatched cabin/party evidence and substituted itineraries on refresh. Children need actual ages, and a possible age-12 fare-boundary crossing is refused. Flexible child calendars are not enabled without birth dates. Expedia partner credentials and live results are not configured/verified here.

### Expedia via Omkar

Configure `OMKAR_API_KEY` using an Omkar account. The adapter uses Omkar's documented one-way endpoint and only requests one adult. It shows a priced offer only when Omkar explicitly identifies a one-way/one-traveler scope and the currency is explicitly CAD; a CAD fare with incomplete schedule detail appears as a labeled price-only observation. Other currencies and unsupported party shapes fail closed. Round trips receive a direct Expedia search link, not a quoted round-trip price. A Selenium scraper is not enabled: current selectors and permission for automated Expedia-page collection have not been verified. No booking or checkout is automated.

Skyscanner uses its official Flights Live Prices create/poll endpoints and itinerary-refresh flow for one-way and round-trip searches. A round trip sends two inverse dated query legs and accepts only offers containing both matching directions; it never adds separate one-way amounts. Incremental polls retain previous result tables unless the provider explicitly replaces them. Price amounts use the documented whole/centi/milli/micro unit; unknown units and fractional-cent totals are withheld. Configure `SKYSCANNER_API_KEY`; access is partner-gated and current round-trip behavior has offline contract tests only. Refresh is a provider quote, not a guaranteed checkout price. Child ages are required; infant/identified parties remain unsupported by this adapter.

### Air Canada NDC

The adapter uses Air Canada's NDC 17.2 aggregation SOAP envelope with `AirShopping` and `OfferPrice`; no booking or payment writes are included. Configure the Air Canada-issued API key, SellerID, accredited IATA/TIDS number, and Agency ID. Optional `AIR_CANADA_NDC_BASE_URL` selects the approved production or GOLD host. Do not substitute documentation example identities. This adapter is mock-tested but not live-verified because no Air Canada credentials were configured.

Successful region lookups are cached locally in `.cache/regions-v11` for seven days. If a refresh fails, the last cached lookup is used and marked stale in the UI. Empty lookups and failures are not cached. Delete that directory to clear the region lookup cache. Successful ITA Matrix API responses are cached in the shared local SQLite job database for five minutes (up to 100 entries, at most 1 MB per response). The cache key is a digest of the validated query and Matrix API key, so raw keys are not stored in the cache. Browser-based Matrix searches bypass it. Other flight prices are fetched anew.

### Booking.com sources

The hotel form separates **Booking.com website search** (the existing human-operated browser path) from **Booking.com Demand API (partner access)**. The Demand API choice runs inside the durable hotel worker and fails closed without `BOOKING_API_TOKEN` and `BOOKING_AFFILIATE_ID`. It resolves a unique Booking.com city ID using the verified city and country, searches at most 30 properties with CAD, products, charge details, requested star class, and exact actual guest/room allocations, then joins static property details by accommodation ID. It only displays a result when the property is in that exact Booking.com city/country, has an official 4–5 star rating, has a safe Booking.com property link, and its product occupancy and CAD display/expected-total amounts match the request. Candidates without these fields are withheld. Search pagination is not followed.

Demand API `book` is the display price and `total` is the expected payable amount including included and excluded/non-conditional charges; conditional charges may still apply. Prices remain search observations, not seller-verified checkout prices. The UI instructs travelers to recheck the room, terms, and expected total on Booking.com. No booking endpoint is called. No Booking.com partner credentials are configured in the current local environment, so the new path has fixture evidence only and has not produced live inventory. Never use sandbox responses as production prices. The browser path accepts validated room-by-room adult/child age allocations and runs one query for each room; it joins only fresh CAD observations for the same verified property and stay. Separate room queries do not prove simultaneous availability, equivalent room categories, mandatory charges or a comparable checkout total. On HTTP 403/429, the browser path stops immediately. Timeout diagnostics expose only bounded status/title/host/path/card-count/challenge-marker metadata; query strings and page captures are not retained. The latest live Montréal child/two-room and one-room diagnostic attempts returned no room observations and are recorded in [docs/hotel-multiroom-live-check-2026-11-08.md](docs/hotel-multiroom-live-check-2026-11-08.md).

When Demand API credentials are configured, a multi-room Flight + Hotel subtotal can use one property's product and expected-total observation only when every requested room allocation (including exact child ages) and product total matches. The UI calls it “observed together in one response”; current availability remains unverified, conditional charges may apply, and flight and hotel are separate purchases. A controlled Chromium check renders this state using intercepted fixture data; it is not live inventory. Details and the exact credential blocker are in [docs/flight-hotel-demand-multiroom-2026-11-08.md](docs/flight-hotel-demand-multiroom-2026-11-08.md).

`POST /api/hotels/search` remains a local-only experimental endpoint and returns no results unless credentials and a verified destination are supplied; the website uses the durable `/api/search/jobs` worker instead. ### Human-operated challenge handoff

The “Find a stay” form starts a durable `kind: hotel` job at `POST /api/search/jobs`. The legacy `/api/browser-jobs` route now bridges to that same queue. The browser stays alive through verification and result extraction. When a recognized challenge container is visible, only its cropped image appears in a modal. Clicking the image relays that user's click to the original browser page; refreshed frames carry IDs, and stale/out-of-bounds clicks are rejected. The first implementation supports clicks, not typing, audio or drag challenges. It never falls back to streaming the entire page. Unknown prompts time out with an error. Cancel closes the browser; sessions also expire after five minutes.

The bridge is provider-independent in `lib/challenge.mjs`; only Booking.com is wired to it so far. Other providers need their own authorized search adapter and verified challenge selectors. The job endpoint requires same-origin localhost requests, serializes hotel browser leases across workers, and stores no personal browser profile. Cookies stay in the ephemeral controlled browser and are discarded when it closes. It requires a local graphical browser executable (default `/usr/bin/chromium`, override `API_ANYTHING_BROWSER`), run headlessly.

Booking.com search pages are parsed with an app-local api-anything operation derived from the captured public result markup. The browser adapter supplies the actual rendered HTML to api-anything through its fetch hook, preserving the browser session rather than transferring challenge tokens. App-specific api-anything state lives in `.cache/api-anything`; it does not use your personal api-anything state. The local spec is not published to the catalog. This is a browser-backed operation, not a proven standalone HTTP replay API.

Only first-page cards with explicit CAD prices, four/five star icons and matching nights/adult counts are accepted. Price and tax strings are preserved separately; no all-in total or discount is invented. Outbound hotel links strip session parameters. Search dates, room counts and child ages are checked against the provider's final URL. Multi-room searches require exact per-room age allocations before a durable job is created; Booking.com browser searches then query each assigned room separately and combine displayed prices only for fresh observations matching the same verified property, destination and stay. These sums are not evidence of simultaneous room availability, equivalent room types, complete fees or checkout totals. Official-site searches also accept validated room allocations. Booking transactions are not supported.

Validation: local controlled challenge test, frontend modal/click test, snapshot extraction against a saved real Booking.com page, and production build pass. Real-provider interactive CAPTCHA completion has not been verified. Live searches may encounter an unrecognized verification page. The older `/api/hotels/search` endpoint is a separate, incomplete official-partner API experiment; the UI uses the independent worker queue.

Destination type defaults to automatic detection using Wikidata exact names or aliases and descriptions. Ambiguous names and lookup outages require a manual override. Region searches use a limited, incomplete airport set and report the selected sources and airports checked.

### Local destination decision model

The app can classify airport, city, country and region descriptions locally with the open Laya decision model. It uses exact Wikidata search results as geographic evidence; the model cannot invent a place, create fares, or override conflicting evidence. A high-confidence model decision that agrees with the evidence is shown as a subtype. A conflict requires a manual choice. During startup, timeouts or when the model is absent, the existing Wikidata classifier remains available.

Run `scripts/setup-laya.sh` to install the CPU-only runtime in `.venv-laya` and download the pinned model into `.cache/laya-model`. First model loading can take over a minute and roughly 2 GiB of RAM on this machine. The worker starts lazily on the first destination lookup; searches while it loads use Wikidata, and later searches can use the model. Inference is offline; Wikidata lookup still uses the network. The model is an open Laya checkpoint, not Jev. Do not treat its confidence as a verified geographic fact.

Airport suggestions use Ignav live lookup with a 10-minute in-process cache and debouncing. An uncached lookup may count against the Ignav account's usage. The calendar runs exact dated Ignav fare queries over a maximum of 31 departure dates, preserving cabin, actual ages and all flight filters. Each price retains its itinerary, quote time and seller lookup; it is the lowest returned matching observation, not a market-wide minimum or confirmed booking.

For adult-only Ignav itineraries, the opt-in separate-ticket comparison refreshes the original fare and searches the same flight numbers and UTC schedules. One-way chains support two–four segments; round trips support one–four segments per direction, including two independently priced nonstop one-way tickets. The default compares whole directions and individual segments; the contiguous-grouping option explores every eligible contiguous partition within each direction. No ticket block spans the destination stay. A 180-minute minimum self-transfer buffer and the requested flight/layover filters apply; the destination stay is excluded from connection time. Its price difference excludes unobserved extras and does not guarantee a saving or available seats.

The comparison has a hard request budget (UI choices 25/50/100/200, default 100). After one baseline refresh, the engine calculates the deduplicated ticket-block/party-size request count and sends no independent-ticket requests if the comparison would exceed that budget. The largest supported round trip with nine adult group sizes needs at most 181 distinct initial requests before recovery, stale-quote refresh or transport retries; shared source pacing/cooldowns still apply. Totals use integer CAD cents and require every ticket plus the baseline to remain fresh. Each displayed comparison expires at the earliest provider expiry or application observation-age limit. Comparisons run in the independent worker, survive reload and support cancellation and pause/resume. Each request intent is durably acknowledged before provider work; interrupted lookups and refreshed stale quotes consume the same hard budget on recovery. These counters count logical fare searches; transport retries can add network requests.

Airline and layover filters exclude offers whose segment data cannot verify the requested condition; source coverage may therefore shrink. Layover windows use observed UTC segment timestamps and apply to both legs. Exact calendar queries apply budget, airline, stop, country and layover filters to actual segments in both directions. The calendar always selects the lowest matching returned price for each date; the main result sort does not change that rule.

Layover-country exclusions use two-letter country codes and resolve intermediate airports through live Wikidata country claims, cached for 24 hours. A maximum of 80 previously uncached airports are resolved per search; ambiguous or unavailable country data causes affected offers to be excluded when this filter is active. This is not a substitute for verified transit/visa rules.

The split-segment option can optionally price adult booking partitions separately on each leg. Independent quotes may overlap inventory; the reported difference is before unknown extras and is not a confirmed saving. The live separate-ticket probe found no eligible two-segment itinerary, so this feature has only controlled-test verification.

### Flight observation age policy

Flight results must carry an ISO observation timestamp and pass the shared flight schema. The app excludes observations older than 15 minutes, timestamps over two minutes ahead of its clock, and expired or malformed provider expiry values when supplied. This is an application age limit, not a seller price guarantee. The main flight card rechecks age every 15 seconds and hides its price/actions after the observation ages out. Start a new search to obtain another observation. Hotel, package and ticket-comparison cards also apply freshness guards. Exact calendar cells apply the same freshness guard. Complete provider expiry extraction and seller revalidation remain pending.

### City and airport input resolution

In the local app's combined-source search, a typed airport name must match the live Ignav lookup exactly. City searches resolve a unique real Wikidata settlement and use airport “place served” (P931) claims to build a bounded airport set. Ambiguous city identities open a city picker with Wikidata evidence. Select a city and submit the search again; the server revalidates its identity. Editing location text clears that selection. Missing claims and the selected location-airport cap can omit airports; the UI discloses the returned candidates and provenance. No static place list is bundled. Exact three-letter codes are validated by the flight providers. Explicit Google-only place queries retain that source's city-name handling. ICAO conversion and broader alias/qualified-name support remain pending.

### Durable local search jobs

Flight, hotel, vacation-package, ticket-comparison and exact-calendar forms use a SQLite queue at `.cache/jobs/search.sqlite` and an independent `npm run worker` process. Both processes must share the project directory/persistent disk, or the same `TRAVEL_JOB_DB` path. The worker loads `.env.local`; keep that file private. Node 22.13+ with built-in SQLite is required. The database is created with mode 0600 in a private directory. It contains search ages, provider observations and session references; never publish it.

A worker processes one search job at a time in an isolated child process. Claims use 30-second leases and fencing tokens so an old worker cannot overwrite a recovered/cancelled job. For flight, calendar and comparison jobs, an expired parent-worker lease can be recovered up to twice within the original 15-minute job window. Voluntary pauses do not consume this crash-recovery budget. Recovery can repeat read-only provider calls already sent before a crash; it does not provide exactly-once external execution. Cancellation revokes the lease, and the worker terminates the active child on its next heartbeat. A provider may still finish a request it already received.

If a child does not exit after SIGTERM, the parent forces termination with SIGKILL after 15 seconds so later jobs are not permanently blocked. Normal exit cancels that timer. This complements browser cleanup and does not cancel requests already received by providers.

For controlled frontend acceptance, run the built local website and `TRAVEL_CHECK_URL=http://127.0.0.1:3000 npm run check:flight-default`. It intercepts every job/provider boundary, verifies no automatic split searches, reload recovery and explicit comparison opt-in, then closes its own browser. It retrieves no real fares.

The queue accepts at most 20 active jobs. Terminal records older than a day are removed on later submissions. The UI reconnects to its saved job reference in session storage after reload and polls with bounded backoff after transport failures. It does not enqueue a new search during reconnection. Completed prices remain subject to the flight age policy.

This is a local, single-disk search queue. Hotel browser sessions now run inside isolated queue workers; live page handles remain in memory only in the owning worker. Broader browser-source retry policies, multi-host databases, multi-user authentication, worker supervision/deployment and comprehensive monitoring remain open requirements.

#### Local SQLite backup and restore

Use `npm run jobs:database -- backup <new-backup-file>` to make a transaction-consistent snapshot of the configured `TRAVEL_JOB_DB` (or the default `.cache/jobs/search.sqlite`). SQLite's `VACUUM INTO` includes committed WAL data. The command checks SQLite integrity, foreign keys, and the job-store schema before publishing the copy. Use `npm run jobs:database -- verify <database-file>` to repeat those checks. Backups are created with mode `0600`; a newly created parent directory is mode `0700`. Existing destination files are never overwritten. The JSON output contains metadata only, not searches or results.

Restore only to a new path: `npm run jobs:database -- restore <verified-backup-file> <new-database-file>`. Restore validates the copy, marks queued/running/paused searches as interrupted, clears leases and challenge images, and closes pending browser interactions. It reports how many active searches were stopped. This prevents starting the worker against a restored database from automatically repeating provider calls or reviving an old CAPTCHA session. Completed results and their original observation data remain in the restored database.

For an authenticated encrypted archive, first create a separate owner-only key file: `npm run jobs:database -- keygen <new-key-file>`. Then set `TRAVEL_JOB_BACKUP_KEY_FILE` for `backup-encrypted`, `verify-encrypted`, and `restore-encrypted` commands. The archive uses AES-256-GCM with a random nonce and authentication tag; encrypted verification decrypts into a private temporary directory before checking SQLite integrity/schema, and restore still writes to a new database and interrupts unfinished jobs. Key files must be regular, non-symlink files with owner-only permissions (`0600`); key reads use no-follow open semantics and are bounded to 129 bytes. Archive verification/restore also use a single no-follow file descriptor from validation through authenticated decryption. Keep the key separate from the archive, protect it with the operating system, and do not put it in source control or logs. Existing `backup` files are still plaintext SQLite and are not converted automatically.

Stop both the website and worker before switching `TRAVEL_JOB_DB` to the restored path and restarting them. Protect all backup copies as sensitive data: they contain traveler ages, search inputs and provider observations. The isolated backup/restore and local-stack checks use disposable data; they do not touch the app database or establish production-data recovery. No automatic backup schedule, offsite recovery, external alerting, or production-data restore drill is provided. This utility does not make public deployment safe.

Flight jobs can pause/resume within their original 15-minute deadline (paused time counts toward that deadline). Pausing revokes the child worker lease; it may take until the next heartbeat to stop local execution. The resolved location scope and each completed airport-pair result are checkpointed before the next pair starts. Fresh completed pairs are reused after resume or worker recovery; expired observations are refreshed, and observations that age out before final aggregation are excluded. An in-flight request not yet checkpointed can repeat. Explicit Google-only place searches retain their existing path and are not checkpointed between Google operations.

### Provider pacing, refusals and transient failures

Flight HTTP calls now share per-provider pacing and cooldown state in the queue database across web/worker processes. The application gap defaults to 1,000 ms between request starts; `TRAVEL_SOURCE_GAP_MS` can set a gap from 100 to 60,000 ms. This is a local usage policy, not a statement of any provider's quota or permitted rate.

HTTP 429 stops the scan without retrying and records a cooldown of at least 60 seconds or the longer server `Retry-After`. HTTP 401/403 stops the scan and records a five-minute cooldown (or a longer server hint). Other long `Retry-After` hints also defer subsequent calls. Source status includes the retry time. The parser supports both delay seconds and HTTP dates, as defined by [HTTP Semantics](https://www.rfc-editor.org/rfc/rfc9110.html#name-retry-after). Cooldowns survive service restarts; changing credentials does not clear an active per-provider cooldown.

Safe GET/HEAD requests, Ignav's read-only fare/link/calendar calls, and Skyscanner polling can retry a transient connection/5xx failure once after bounded backoff and shared pacing. They never retry 401/403/429. Search-session creation and NDC POSTs are not replayed automatically. Google requests remain under API Anything's execution policy, with application pacing/cooldowns and preserved rate-limit diagnostics. No booking/payment operation is introduced. Transient retries may still incur provider usage. Browser hotel/package execution and their source-specific policies remain separate work.


### Queued vacation packages

`POST /api/search/jobs` accepts `kind: package` on start, with an explicitly validated package query. Package status, result/error, progress and cancellation are durable and survive page reload. The package form uses a separate session-storage reference from flights. One package browser job may own a live lease at a time across workers, with a brief cancellation cleanup window. Cancellation aborts the job and closes Chromium; prices are hidden after the application observation age limit.

Package browser jobs support cancellation rather than pause/resume. If a browser/worker lease is lost, the job becomes an error and requires an explicit new search; the provider submission is not replayed automatically. Queued packages can wait for a worker, and a provider booking-widget outage is reported explicitly. This does not establish live package bookability.

`POST /api/packages/search` is now an enqueue endpoint: it returns HTTP 202 and a job reference, rather than waiting for observations. Send `Idempotency-Key` to deduplicate starts and poll `/api/search/jobs` with `action: status`. The package form uses provider-returned exact location labels and supports 1–6 adults plus up to eight children aged 2–17 (nine travelers total) in one room. Infants and child parties across multiple rooms are not supported. Completed results repeat the searched location/airport, dates, adult count, exact child ages at departure, derived lap-infant age by direction, room count, hotel class, stop/budget filters and result cap beside the cards; CAD totals use two decimal places and thousands separators. The provider result parser and live adapter remain bounded to the selected 20- or 40-card limit; checkout availability, local charges and exact property-to-destination matching are unverified.


### Durable hotel sessions and human verification

Hotel requests, job state, progress and results now use the same private SQLite queue and independent worker as flights/packages. The main form has its own reload-recovery reference. Browser leases are serialized per product; lost hotel browser leases end in a durable error and require an explicit fresh search. Cancellation closes Chromium, including a browser that finishes launching after cancellation. Browser launches time out after ten seconds; a stopped child has up to fifteen seconds for cleanup, with a seventeen-second cross-worker browser cleanup slot.

Recognized verification frames remain cropped images from the original browser. Human clicks and refresh requests go through durable, deduplicated commands (`action: interact`, `input.kind: click | refresh`, a unique requestKey). The server checks job ownership, current image ID, age and bounds; the owning browser checks again before applying the click. Commands are not replayed after losing the browser session. Terminal jobs clear their active challenge image and end any pending commands. SQLite files/WAL may retain prior pages; keep the entire private cache protected and never publish it. No CAPTCHA answers are generated automatically.

Hotel cards and selected flight/add-on price displays now use observation-age guards. Combined arithmetic excludes stale quotes; all-in totals, live property-address extraction, availability and property-specific occupancy/policy evidence still require further verification. A live Montréal probe did not yield a verified-format result in its bounded test window and was explicitly cancelled; this is not evidence that no rooms were available.


### Matching a hotel to the selected flight

The hotel add-on sends the observed arrival airport and retains any city choice already made for the flight. The worker uses live Wikidata settlement/country and airport P931 claims to resolve a served city; multiple supported cities require a choice. If geographic evidence is unavailable, independent hotel observations can still be displayed with an unverified-location label, and no combined subtotal is shown.

For a resolved flight destination, the browser inspects up to five observed Booking.com property links in the existing browser context. It requires the same property identity and hotel name, plus a structured [Hotel](https://schema.org/Hotel)/[PostalAddress](https://schema.org/PostalAddress) locality and country matching the verified city. It stops additional location checks on a property-page access refusal or recognized verification. Source URLs in location evidence omit query/session parameters. Missing, conflicting or differently localized address/name data remains unverified; no fuzzy matching invents a location.

A subtotal now requires matching arrival airport, city identity, country, property key/name, current address observation, dates, occupancy and current CAD quotes. It is still an independent observed subtotal; taxes, fees, availability and booking protection may differ at checkout. The geography link and structured parser have test evidence, while live Booking.com property markup/result extraction remains unverified in this environment.

### Durable ticket comparisons

Start `kind: comparison` through `/api/search/jobs` with `input.mode: party | segments`. Inputs require exact airport codes, dates, cabin and an adult-only party; segment mode also requires the observed itinerary key and accepts contiguous-group, adult-split, request-budget and minimum self-transfer buffer settings. The UI restores the job and its options for the matching trip/itinerary, without submitting a new comparison. Different filters or itineraries keep separate saved references.

Both `/api/search/optimize` and `/api/search/separate-tickets` now enqueue and return HTTP 202 plus a job reference. Send `Idempotency-Key` to deduplicate legacy-route submissions; poll/control the returned ID through `/api/search/jobs`. They no longer wait for pricing in a web request. Comparison jobs share the normal 15-minute deadline and queue capacity, serialize their active leases across workers, and allow pause/resume/cancel. Paused time counts toward the deadline.

Each comparison checkpoint preserves its validated input signature, request count, pending request intent and completed fare responses. The child waits for the database acknowledgement before each read and before continuing after a response. Fresh responses are reused on resume/recovery; stale ones require another budgeted lookup. A pending intent is conservatively counted as interrupted even if the provider never received it. Repeating that read consumes another budget slot. Exhausting the budget returns no claimed complete plan; it never resets the counter or silently increases the limit. Source pacing/cooldowns and actual seller/quote limitations still apply. Provider requests already sent may finish after cancellation.

### Exact fare calendar

The date explorer now uses `kind: calendar` jobs. `POST /api/search/calendar` enqueues and returns HTTP 202 plus a job reference; it accepts `Idempotency-Key` and no longer returns the supplier's unverified cheapest-date indications. Poll/control the job through `/api/search/jobs`, which also accepts calendar starts directly. The lower-level `getIgnavCalendar` helper still describes supplier indications and is not used for UI prices.

A calendar query requires exact airport codes, explicit adult/child counts and actual child ages, cabin, first/last departure dates, trip type, and a selected source. Ignav supports round trips, identified parties, and date ranges. Skyscanner calendar searches are one-way only because its API returns airport-local times without timezone offsets; identified travelers and layover-time windows are refused, and child ages are allowed only for a single departure date. Skyscanner's API key is server-side, each query may poll up to eight times, and incomplete searches are withheld. Both sources return CAD only. Round trips require a stay length of 0–365 nights; each return date is that departure date plus the selected number of nights. One-way calendars have no return date. Ranges include at most 31 departure dates. One logical fare search is sent per airport pair/date; default budget 62, configurable up to 100. Recovery/interruption and stale-quote refresh consume this same budget. Shared pacing/cooldowns and transport retry limits apply.

The worker validates current CAD itineraries and their actual segment chains, applies supported flight filters, and selects the lowest remaining fresh group quote per date. Empty or filtered dates show no matching observation; dates not reached after a source refusal or budget stop are explicitly unscanned. Fresh earlier observations remain visible after a partial scan. Missing taxes, extras or seller inventory are never inferred. Ignav cells can request seller options; Skyscanner cells link to the provider handoff without claiming a refreshed seller price. Stale prices and actions disappear.

Progress, cancellation, pause/resume, acknowledged request/response checkpoints and reload restoration use the normal durable queue and 15-minute deadline. Calendar references are independent of flight/comparison references. An untouched flight form restores the calendar's actual saved query after reload. Selecting a date loads that cell's dates and saved route, party, cabin and filters into the flight form, so an edited draft cannot silently change the quote's context. Regional/multi-airport calendar expansion is implemented over bounded resolved airport sets. No Skyscanner API key is configured in the current environment, so the new Skyscanner calendar adapter has fixture and UI/API-boundary coverage but no live Skyscanner fare evidence. Final all-in seller availability remains unfinished.

Matrix search response timeout defaults to 90 seconds. Set `TRAVEL_MATRIX_RESPONSE_TIMEOUT_MS` to a whole number from 1000 to 180000 milliseconds to change it. Browser form setup has a separate bounded 20-second allowance; cancellation and per-route timeout isolation remain active.
