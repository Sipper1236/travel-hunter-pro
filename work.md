## 2. Original product vision and required search modes

### 2.1 Flights — ITA Matrix-like advanced search

The Flights tab must support:

- Origin and destination selection, including city, airport, country, multi-airport areas, and geographical regions.
- One-way and return trips, departure and return dates, date flexibility, desired length of stay, and lowest-fare calendar results.
- Economy, Premium Economy, Business, and First Class.
- Sorting by lowest or highest price, verified elapsed journey duration, departure time, and other useful attributes. Current partial evidence (2026-11-08): duration sort and limits derive from exact offset-aware segment timelines and include layovers; sources without such timelines are reported as unknown and cannot pass a selected duration limit. ## 3. Passenger modeling — essential requirements

Passenger count is not just a number. User repeatedly stressed **adults, children, and youths**, and later asked that no invented traveler identity, ages, or known passenger counts be used except from user input.

### 3.1 Canonical traveler model

Recommended internal traveler record:

```ts
type Traveler = {
  id: string;
  ageAtDeparture: number;        // provided by user, not guessed
  categoryHint?: "adult" | "youth" | "child" | "infant";
  dateOfBirth?: string;          // optional, securely handled
  lapInfant?: boolean;
};

type Party = {
  travelers: Traveler[];
  rooms?: number;
};
```

The UI should accept counts and then request the ages that materially affect eligibility/prices, or directly accept age per nonadult traveler. A passenger's carrier-specific age category depends on the airline, ticket and fare conditions, route, booking channel, and travel dates. **Never assume every 15-year-old is automatically a “youth” under a given fare.** Booking.com accommodation occupancy policies also use property-specific age rules and child's age. The earlier prototype's hard-coded 10-year-old children and the example `11, 13, 15` are illustrative only, **not real user values**.

### 3.2 Standard and opt-in split-party search

Default: search the full group on a single booking. Deep Cheapest Search ON: generate legal partitions of the travelers into alternative reservations, such as:

- For 2 adults + 3 young travelers: all five together; 4+1; 3+2; 2+2+1, and other valid allocations.
- A partition must retain each individual's actual age, and comply with unaccompanied-minor, infant-with-adult, seat/booking, and carrier youth-fare requirements.
- Distinguish **separate booking references (PNRs)** from **physically separate flights**; a 4+1 split on the *same flight* and a 4+1 split on *different flights* are not equivalent and should have distinct safety/coordination rules.
- Compare seat-inventory effects, group pricing, different carriers, classes, tickets, separate payment carts, and total taxes/fees.
- Track independent inventory and temporal consistency; separately observed quotes may disappear before checkout.
- Avoid presenting separated minors on unrelated flights as an ordinary cheap option without guardian/legal-eligibility validation.

### 3.3 Separate-ticket **segments** as well as passenger partitions

This later clarification was particularly important: for **YHZ → Barcelona (BCN)**, compare a through fare (e.g., YHZ–YUL–BCN as a single ticket) with independently priced YHZ–YUL and YUL–BCN tickets, possibly each itself sold in a 4+1 or 2+3 passenger partition. Do this for relevant intermediate airports and route combinations.

For each candidate itinerary:

1. Identify the actual flown segment chain and available dates/times.
2. Price the whole itinerary as one through-ticket for the full group and relevant permitted passenger splits.
3. Price every individual segment (and permitted contiguous segment groupings) as one or more independent reservations.
4. Optionally compare split reservations *per segment*, subject to all travelers reaching the same destination and maintaining a viable connection.
5. Calculate `segment 1 prices + segment 2 prices + …` including any mandatory airport-transfer, checked-bag, recheck, entry, visa, and service costs supported by source evidence.
6. Compare with the baseline through fare: `savings = comparable through-ticket total − comparable separate-ticket total`.
7. Show the source/provider and check-out method for **every segment and passenger group**, not merely for the combined itinerary.
8. State explicitly if the result has separate tickets/PNRs, is self-transfer, has unprotected connections, may require baggage reclaim, or requires agent handling.
9. Respect realistic connection minimums and the user-configured layover window. Separate tickets commonly need a *larger practical connection buffer* than a protected through-ticket; do not treat the airline's minimum connection time as sufficient for an unprotected self-transfer.
10. Revalidate actual inventory, prices, operating flights, terminals, entry/exit requirements, and combinability before presenting the result as actionable.

## 12. Algorithmic approach for deep route and pricing exploration

The user requested very broad and thorough search, even if it takes longer. **Literal exhaustive worldwide search cannot be guaranteed** because schedules, supplier visibility, fares, rate limits, interline constraints, married-segment logic, and rapidly changing inventory make the search space enormous and incomplete. Implement a *bounded, transparent, depth-configurable search* with a clear coverage report.

### 12.1 Discovery phase

1. Resolve typed airport/city/country/region into eligible airports, no silent static exclusions.
2. Discover schedule/flight legs and possible connections from actual data sources.
3. Form a time-expanded graph with airport, departure time, arrival time, carrier, ticket seller, and connection feasibility.
4. Apply country exclusions, max stops, min/max layover, visa/transfer constraints, and travel-duration limits.
5. Preserve audit records of airports explored, suppliers queried, date windows, skipped sources, and errors.

### 12.2 Price-search phase

1. Search through fares for the full group.
2. If **Deep Cheapest Search is OFF**, do not search passenger splits or separate-ticket permutations.
3. If ON, generate legal traveler partitions subject to age and supervision constraints.
4. Search each relevant booking group for candidate flights and fare classes.
5. For each physically feasible route, price through tickets and every sensible contiguous segment partition (not only each individual hop).
6. Compare *jointly feasible* tickets for each passenger group and segment; allow booking groups to differ between route sections only if traveler assignment and itinerary timing remain coherent.
7. Minimize actual total cost via a constrained optimization process, including user-defined costs/penalties for unprotected transfers and itinerary inconvenience.
8. Recheck the best combinations at the sources before display, with warning and a fresh observed-at timestamp.
9. Deduplicate identical results from different sources while retaining all sellers/prices and source evidence.
10. Present an explicit “coverage so far” breakdown rather than falsely saying all combinations were found.

### 12.3 Safety and real-world checks

- Cannot strand a child/youth on an unaccompanied route unless airline rules and guardian approvals permit it.
- Infant seating, age-at-travel, adult-to-infant ratios, special assistance, and transit-country rules must be validated per carrier.
- Hidden-city ticketing, skip-leg ideas, back-to-back ticketing and other policy-sensitive practices were **not requested** and should not be silently used.
- Self-transfer risks: delayed incoming leg may not protect onward booking; baggage may require claim and recheck; overnight stops and entry requirements may apply.
- Separate-ticket fares may be cheaper but can be riskier; display that trade-off prominently and consider an option to disallow self-transfers.
- Booking partner may require same flight/PNR for minors, and travel-agency issuance may have fees.

## 15. Problems in historical code or claims requiring remediation

The following are specific risks revealed or strongly indicated by the conversation's code snippets and diagnostic behavior:

1. **Demo fallback contaminating live results.** Historical `searchPartyVariant` chose demo flights if a live provider returned no offers. Live mode must not do that.
2. **Fake supplier attribution.** Demo results sometimes labeled Sabre/Hahn Air/Costco despite no connected inventory. Source assertions require provenance.
3. **Incomplete split-party rules.** Some example algorithms partition adults/children without exact ages; youth categorization and child supervision require per-supplier validation.
4. **Split result aggregation not guaranteed to be the same flights.** Combining the cheapest independent group offers by destination alone can produce a “joint itinerary” whose groups travel on different departure dates/times. Make co-travel requirements explicit and use actual itinerary identity.
5. **Fare combination lacks price comparability.** Compare identical currencies, date windows, cabins, traveler inventory, directions, and mandatory extras.
6. **Separate-ticket engine had partial graph logic.** Combining segments on endpoints alone is insufficient: needs actual chronological feasibility, arrival/departure airports, minimum transfer times, and legal transit.
7. **Per-person totals can be misleading.** Divide by travelers only for an explicitly labeled average; retain passenger-specific fare categories and group totals.
8. **One-way/return handling may be inconsistent.** Example segment planner sometimes synthesized an inbound display path without actually pricing return segments. Return legs must be separate observed quotes.
9. **Hotel occupancy validation incomplete.** A historical Booking.com adapter used an array of arbitrary 10-year-old children; exact ages and room allocation matter.
10. **Package mode may mix incompatible destinations.** A region-wide flight result and a fixed `Lisbon` hotel result must not be combined unless flight destination and hotel location actually match.
11. **Currency conversion was not proven.** A CAD label does not guarantee real exchange conversion with correct rate, timestamp, fees, and source currency.
12. **Fare calendar demo math.** Date cells generated by a deterministic formula are not acceptable as lowest observed fares.
13. **No authentic agent price without GDS entitlement.** UI toggles alone cannot expose Sabre, Travelport, or Hahn Air private inventory.
14. **Worker template returned empty results.** Confirmed in user screenshot; the actual live scraping/search engine was never completed.
15. **Dynamic airport lookup may be unreliable.** Public SPARQL endpoint may be slow, rate-limited or incomplete; no production fallback confirmed.
16. **Full world search infeasible without a coverage budget.** A responsible app should disclose checked combinations and sources, with search depth configurable.
17. **No durable job service.** In-memory Map and microtasks are not production-ready background execution.
18. **No end-to-end production build confirmation for latest version.** Historical reports often cited TS/TSX syntax checks because npm failed in the assistant environment.
19. **Early dependency vulnerability.** An npm audit reported one critical vulnerability; needs a current security check and upgrade plan.
20. **Potential legal, compliance, and anti-bot restrictions.** Live browser automation must honor applicable website terms, access controls, and rate limits. The app must not offer CAPTCHA bypass or unauthorized access as its default integration method.
21. **Progress UI semantics.** A diagnostic item can retain “running” after the job finished; overall job status should be clearly separated from event history.
22. **Schema examples not consistent.** At one point a suggested Playwright worker consumed `payload.origin` while the backend sends nested `payload.flight.origin` and used `"ok"` outside the declared diagnostic enum.
23. **No booking transaction capability.** Finding a price is different from ticketing or completing a reservation. The application did not demonstrate actual payment, ticket issuance, provider confirmation, or hotel reservation confirmation.
24. **No proven final downloaded ZIP current integrity.** Previous archive links and source snapshots were from earlier turns; this report does not certify their continued availability or contents.

## 18. Recommended implementation order

1. **Stabilize the current app and remove all misleading demo pricing.** Keep only the existing UI and genuinely functioning worker APIs.
2. **Finalize schemas first:** traveler exact ages, route legs, provider provenance, ticket grouping, hotel occupancy, and price/fee inclusions.
3. **Make the airport dropdown functional against a live lookup** and accurately distinguish airport, city, country and region input types.
4. **Implement one permissible live flight adapter** and prove reliable extraction with a documented source and quote timestamp. Do not label placeholders as real GDS.
5. **Add a second flight source and a common normalizer**; test deduplication and recheck prices.
6. **Implement the split-party + separate-ticket optimizer** on real observed segments, with time feasibility, minors, and independent booking warnings.
7. **Add official hotel/Booking.com sources**, correct occupancy, and Flight + Hotel incremental totals.
8. **Add supplier vacation packages, CAA, Costco and verified promotions.**
9. **Add geographic Explore and real cheapest-fare calendar**, driven by real quote observations.
10. **Replace prototype job state with durable orchestration**, add telemetry/security/test suites, and prepare for deployment.

Suggested milestone gate: do not move from P0 to broader route enumeration until a single actual live source returns accurate, repeatable results in a UI search. A polished interface with empty workers is not a production travel engine.
